archon

ἄρχων

Ed25519 identity — keys, one canonical way to write them, the standard PEM containers, and domain-separated signing — implemented separately in Rust, Go and TypeScript, and proven to produce the same bytes in all three.

The three are not bindings over a shared core. They are three real implementations, held byte-identical by an oracle hand-authored from the RFCs — including the cases where Ed25519 libraries genuinely disagree with each other.

Standing on that floor, in this repository and to the same discipline: an sdk — proof of possession, a signed envelope, and the login scheme built on the first — and the archon command. Each written three times; each pinned by its own oracle.

The shape

Why three implementations, and not one with bindings

Because the guarantee is about bytes crossing a language boundary. A key written by a Rust service and read by a Go daemon has to be the same key, and a binding proves nothing about that — it just moves one implementation around.

So archon writes its encodings three times, and never the curve. Each core binds its language's mature, audited Ed25519 and adds nothing to it:

Runtime dependencies, in full: ed25519-dalek · none — Go stdlib · @noble/ed25519 + @noble/hashes. Constellation dependencies: dependsOn: []. CI needs no credential to build archon, because archon depends on nothing private.

The proof

Three Ed25519 libraries really do disagree

This is not a hypothetical the harness guards against. It is a divergence that was live in this repository's own TypeScript core, and the vectors now pin it shut.

The instrument

How agreement is established

Each core is driven as a black box against a reference document it cannot see the answers in — so every core is checked against the standard, and only therefore against the others.

The surface

Fifteen functions, four modules

That is the entire public API in each language. Note the signatures: the cores agree on bytes, not on call shapes — each door is idiomatic to its language, so argument order and error style differ on purpose.

crypto

Ed25519 over canonical bytes (RFC 8032). The message is whatever byte sequence the caller defines — archon has no opinion about what it means. Two ways to sign: raw, where the caller owns separation; and in a domain — Ed25519ph with the caller's domain as context — where a signature from one protocol can never verify in another, or raw, whatever the bytes.

The mechanism

How three languages agree on DER without three ASN.1 libraries

An Ed25519 key container is fixed-size. So encoding is a constant prefix with the 32 key bytes spliced in, and decoding is a bounded template match — small enough to read in full, and identical in every language.

Above the floor

The floor, and what stands on it

Three things stand on the floor in this repository, to the same discipline: an sdk that answers the next questions every protocol asks — can they sign for this channel? are these bytes theirs? may this ephemeral key act as them? — the archon command, and the login server a service mounts to answer the last one. Each is written three times; and every edge between them is a line in a manifest: the sdk on the floor alone; the command and the server on the floor and on the sdk's login scheme, which they consume and never re-implement.

Attach

Three doors, one command

The doors are peers — none is a binding over another. Rust is named canonical only for settling a semantics dispute, and in practice the three cannot drift apart: CI fails on the first disagreement. The floor's coordinates first; the sdk and the command attach the same way, one line under each.

Before you build on it

The rules that change how it is used

verify fails closed

Every shape failure — wrong-sized key or signature, malformed point — collapses to false. It never panics and never throws. That is deliberate: Go's stdlib ed25519.Verify panics on a mis-sized public key, making every unguarded call site a latent crash. Writing the guard once, pinned across three languages, is a large part of why this repository exists.

derive panics on a bad seed

Asymmetric with verify, on purpose. A seed that is not 32 bytes is a programming error, not a runtime condition to handle — so it fails loudly rather than silently.

it holds no key

The codec reads no file, writes no file, and draws no randomness. seedToPkcs8Pem takes a seed it is given; it never invents one. Key generation is custody, and custody is a security boundary that lives in a repository you have to go get.

it has no opinion about authority

No is_root, no admission, no grants — those words appear nowhere in the code, only in comments explaining their absence. That a signature is well-formed is archon's; what a signature means belongs to the layer above.

the key is the principal

There is no rotation-preserving identity and no re-key path. Loss or compromise means re-genesis. If you need succession, it is not here and was deliberately not taken.

PKCS#8 v1 only, PEM only

v2 with an embedded public key is rejected; bare DER without armor is rejected; each decoder rejects the other's PEM. Decode is total — any shape it does not recognise is a clean error, never a partial result.

Deliberately not owned — measured, not assumed

  • Succession, rotation, epochs — owned by the law layer above, and independently re-ruled there.
  • The possession protocol — the handshake, the custody-mode discriminator, the connection itself: the transport's. The scheme — what is signed, with what binding — was re-ruled into the sdk on 2026-09-09 (ADR 0004), because the repository that owned it had the vocabulary and no code.
  • Connection setup — the sdk hands a server the bytes to move and never opens a socket. It is the transport.
  • Expiry, issuer, audience, key-id — each is policy or a second spelling of the key. The envelope is JWS, never JWT, and stays that way.
  • Root trust-anchor designations — removed from all three cores. That is authority vocabulary.
  • Key generation, storage, encryption at rest — custody.
  • A Merkle inclusion primitive — argued for, then withdrawn after the argument was refuted.

The honest test

When not to adopt archon

The nearest adjacent consumer archon could plausibly have served needed Ed25519 and could not import the layer above. archon asked whether it should be the backend — and sent its own answer, no, as the question. It was confirmed, with measurements:

At that consumer's seam
key / signature typesraw bytes
hand-authored vectors carrying a signer0
SPKI / PKCS-8 / PEM anywhere0
ed25519:<hex> spellings0
That repository already had a canonical byte-to-text spelling of its own. Introducing ed25519:<hex> beside it would create the second spelling archon exists to eliminate. docs/extraction-plan.md §4

The general rule, and it is the one to apply to your own repository: archon replaces N spellings with one. That is a strong argument in a codebase with zero canonical spellings across several languages, and an argument against archon in a codebase that already has exactly one. Its value is real and it is not universal — a ten-line direct call to a mature Ed25519 crate is the thing a dependency wraps, not a dependency.

Status

The floor the law above stands on

Three cores, a dependency list you can read in one breath, and a harness that turns "the cores agreed once" into "the cores agree". The switch is done. The law layer above deleted its own copy of these bytes and now links these — stele since 2026-08-23, thesmos since 2026-08-27 — so there is one implementation of the identity floor, and it is this one. What the law keeps is its own trust anchor, which it now pins through this derivation rather than beside it.
