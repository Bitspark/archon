# Releasing

A release is one commit on `main`, one version in every manifest, five tags, one
`workflow_dispatch`. The [language matrix](docs/languages.md) records implementation,
conformance and publication separately, because a tag does not claim an upload to every
registry, and a registry step that did not run is not a registry that published.

The current release is **0.6.2**. Published versions and tags are immutable: a version burned
on a registry stays burned, a tag is never moved (`release-tags-immutable` refuses it), and a
correction is the next version.

## What a version is

[ADR 0005](docs/architecture/decisions/0005-the-layers-version-with-the-floor.md): the four
tiers — `core`, `sdk`, `cli`, `server` — version **in lockstep with the floor**, in every
language, so a consumer names one number. Before 1.0 a change to what a core *accepts* or
emits, to a wire layout, or to a public API increments the minor; a compatible correction
increments the patch. A narrowing of the accepted set is a minor, and says so (0.7.0).

The version lives in **nine manifests plus one self-report**, and the release workflow
refuses a tag that any of them disagrees with:

| site | file(s) |
|---|---|
| npm | `core/ts`, `sdk/ts`, `cli/ts`, `server/ts` — `package.json` (lockfiles regenerated by `npm install --package-lock-only`) |
| crates.io | `core/rs`, `sdk/rs`, `cli/rs`, `server/rs` — `Cargo.toml`, including the inter-tier `version = "…"` on each `path` dependency (lockfiles regenerated by `cargo update --workspace`) |
| PyPI | `core/py/pyproject.toml`, and `archon_core.__version__` in `core/py/src/archon_core/__init__.py` |
| Go | `sdk/go`, `cli/go`, `server/go` — the `require` lines naming the lower tiers, and `go.work`'s `replace` lines (`go install` does not see `go.work`, so the `require` lines are version sites) |

Go publishes nothing: the module proxy fetches from this repository on demand, so **the
per-module tags are the Go release** — `core/go/vX`, `sdk/go/vX`, `cli/go/vX`, `server/go/vX`
beside the family tag `vX`.

## The procedure

1. **Land the release commit on `main`** through a PR like any other: the version bump and
   whatever it releases, with `node conformance/check.mjs` (nine builds, four oracles, three
   tiers) and the per-language jobs green. The commit that is tagged is the tip of `main`.
2. **Tag it, five times, in one push.**
   ```
   git tag -a vX -m "archon vX" <sha>
   for m in core sdk cli server; do git tag -a $m/go/vX -m "archon $m/go/vX" <sha>; done
   git push origin vX core/go/vX sdk/go/vX cli/go/vX server/go/vX
   ```
   ⛔ **A push of more than three tags fires no `push` event.** That is deliberate here: the
   tags go up silently and the workflow is started by hand. Pushing `vX` *alone* would start
   a real release run on the push event instead — do not.
3. **Rehearse.** `gh workflow run release.yml --ref main -f tag=vX -f rehearse=true`. The run
   waits on the `release` environment for its reviewer, then checks the tag against `HEAD`,
   every manifest against the tag, the four Go module tags, tri-core agreement, npm
   provenance's preconditions, dry-run packs of the four npm packages and the four crates,
   and the Python sdist and wheel. **A rehearsal cannot prove a credential**: a dry run never
   authenticates, and neither registry validates a trusted-publisher configuration when it is
   saved. It also cannot verify a dependent crate: the floor was deliberately not uploaded,
   so `sdk`, `cli` and `server` fail to resolve it, and that one failure — in either of the
   two ways cargo spells it — is tolerated in a rehearsal and nowhere else.
4. **Release.** The same dispatch with `rehearse=false`. It waits at the environment gate
   again — the reviewer's approval is the publish decision — then publishes in dependency
   order, waits for each registry to *serve* what it accepted, installs the floor from
   nothing and imports it, and creates the GitHub release with `--verify-tag`.
5. **Read the run, not the exit code.** Each publish step skips what its registry already
   has, so a run that failed after uploading is re-run with the same dispatch and finishes
   the rest. "The publish steps SUCCEEDED — check the registry before assuming the release
   failed" is printed by the round-trip steps for exactly this reason.

The workflow file a dispatch runs is **main's**, while the source it checks out is the tag's.
A workflow fix therefore applies to an already-tagged release without re-tagging; a source
fix does not, and needs the next version.

## Registries and credentials

| registry | packages | how it authenticates | armed by |
|---|---|---|---|
| npmjs (`@bitspark` scope, `registry.npmjs.org` explicitly — a local GitHub Packages scope setting cannot redirect it) | `@bitspark/archon`, `-sdk`, `-cli`, `-server`, with provenance | trusted publishing (OIDC): repo `Bitspark/archon`, workflow `release.yml`, environment `release`. No token in the workflow; leaving `NODE_AUTH_TOKEN` there would make npm use it and OIDC would never be exercised | configured on npmjs |
| crates.io | `bitspark-archon-core`, `-sdk`, `-server`, `-cli` (the prefix is a registry name; the library targets are `archon_*`) | trusted publishing via `rust-lang/crates-io-auth-action`; `CARGO_REGISTRY_TOKEN` remains only as the fallback and can be deleted once a release has gone out on OIDC | `vars.CRATES_IO_TRUSTED_PUBLISHING=true` |
| Go proxy + checksum database | `github.com/Bitspark/archon/{core,sdk,cli,server}/go` | none — the tags | the five tags |
| PyPI | `bitspark-archon-core` (import `archon_core`) | trusted publishing via `pypa/gh-action-pypi-publish`; a **pending** publisher may be registered before the project exists — project `bitspark-archon-core`, owner `Bitspark`, repository `archon`, workflow `release.yml`, environment `release` — so no token is ever needed | `vars.PYPI_TRUSTED_PUBLISHING=true`; unarmed, the distributions are built and the run **warns** instead of failing after npm and crates.io have published |
| Maven Central (`dev.bitspark`) | `dev.bitspark:archon-core` | repository secrets `MAVEN_CENTRAL_USERNAME` / `MAVEN_CENTRAL_PASSWORD` (a Central Portal token pair, not a login) and `MAVEN_GPG_PRIVATE_KEY` / `MAVEN_GPG_PASSPHRASE` (fingerprint `A49669B73C7462D05870C0DECB3E10222F8E5BBB`, public key on `keyserver.ubuntu.com`); the same pair and key that published `dev.bitspark:bitwire` | installed 2026-09-21; the publish step is pending with the Java tier |

Trusted-publisher fields are case-sensitive and unvalidated at save time; a typo is an auth
failure at publish time. A Maven 401 is not evidence that a secret was mis-set: Bitwire's
investigation showed a credential pair reaching Maven unchanged and being refused by Central
itself, and a fresh pair succeeding — diagnose with a read-only request before rotating.

## Recovery

If a run fails after some registry accepted an upload: keep the tag, keep the artifacts,
inspect the registry before doing anything, and re-run the **same** dispatch — every publish
step is idempotent against what is already served, and the round trips are separate steps.
A consumer check that fails after an upload does not mean the upload failed; the registries
serve later than they accept, and the round trips wait for that with a bounded retry. Never
replace a published version with changed source. A registry is "published" in the matrix
only when its public, unauthenticated installation check has passed.

## Not yet in the workflow

Swift, C++ and Haskell will be consumed from the immutable public tag (SwiftPM through the
Git URL, C++ as tagged source with an installed CMake package, Haskell through Cabal's
`source-repository-package` pinned to the release commit; Hackage deferred). They get a
verification-only workflow that builds the exact public release SHA and never uploads,
once the bindings exist — see [ADR 0008 §8](docs/architecture/decisions/0008-the-ed25519-verification-profile.md)
for what they must bind.
