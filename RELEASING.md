# Releasing

A release is one commit on `main`, one version in every manifest, five tags, one
`workflow_dispatch`. The [language matrix](docs/languages.md) records implementation,
conformance and publication separately, because a tag does not claim an upload to every
registry, and a registry step that did not run is not a registry that published.

The current release is **0.7.0**. Published versions and tags are immutable: a version burned
on a registry stays burned, a tag is never moved (`release-tags-immutable` refuses it), and a
correction is the next version.

## What a version is

[ADR 0005](docs/architecture/decisions/0005-the-layers-version-with-the-floor.md): the four
tiers — `core`, `sdk`, `cli`, `server` — version **in lockstep with the floor**, in every
language, so a consumer names one number. Before 1.0 a change to what a core *accepts* or
emits, to a wire layout, or to a public API increments the minor; a compatible correction
increments the patch. A narrowing of the accepted set is a minor, and says so (0.7.0).

The version lives in **every manifest, every self-report, and every inter-tier range that is
not rewritten at publish time**, and the release workflow refuses a tag that any of them
disagrees with:

| site | file(s) |
|---|---|
| npm | `core/ts`, `sdk/ts`, `cli/ts`, `server/ts` — `package.json` (lockfiles regenerated by `npm install --package-lock-only`) |
| crates.io | `core/rs`, `sdk/rs`, `cli/rs`, `server/rs` — `Cargo.toml`, including the inter-tier `version = "…"` on each `path` dependency (lockfiles regenerated by `cargo update --workspace`) |
| PyPI | `core/py/pyproject.toml` and `sdk/py/pyproject.toml`; `archon_core.__version__` and `archon_sdk.__version__` in each package's `__init__.py`; and the sdk's floor range, `bitspark-archon-core~=X`, in `sdk/py/pyproject.toml` — a pyproject has no `file:` link for a publish step to rewrite, so the range is a version site of its own and the guard holds it to the tag |
| Go | `sdk/go`, `cli/go`, `server/go` — the `require` lines naming the lower tiers, and `go.work`'s `replace` lines (`go install` does not see `go.work`, so the `require` lines are version sites) |
| C++ (from the tag) | `core/cpp/CMakeLists.txt` — the `project(archon_core … VERSION …)` line, which becomes `archon-config-version.cmake` and answers a consumer's `find_package(archon 0.8)` |
| Haskell (from the tag) | `core/hs/bitspark-archon-core.cabal` — the `version:` field, which Cabal checks a consumer's bounds against |
| Swift (from the tag) | **none** — SwiftPM reads the version from the tag itself (it accepts the `v` prefix), so nothing in the tree can disagree with it |

Go publishes nothing: the module proxy fetches from this repository on demand, so **the
per-module tags are the Go release** — `core/go/vX`, `sdk/go/vX`, `cli/go/vX`, `server/go/vX`
beside the family tag `vX`.

A package check **derives** the version from the manifest it checks and never repeats the
number: a check that names `archon-core-0.6.2.jar` after the pom moved to 0.7.0 goes red
saying "the artifact is broken" when it means "the script is stale", and the next person
spends the afternoon on the jar. The Python check globs for the built wheel; the Java check
reads `pom.xml`; the next language's does likewise.

## The procedure

1. **Land the release commit on `main`** through a PR like any other: the version bump and
   whatever it releases, with `node conformance/check.mjs` (nine builds, four oracles, three
   tiers) and the per-language jobs green. The commit that is tagged is the tip of `main`.
2. **Tag it, five times, in one push.**
   ```
   git tag -a vX -m "archon vX" <sha>
   for m in core sdk cli server; do git tag -a $m/go/vX -m "archon $m/go/vX" <sha>; done
   git push origin vX core/go/vX sdk/go/vX cli/go/vX server/go/vX
   ```
   ⛔ **A push of more than three tags fires no `push` event.** That is deliberate here: the
   tags go up silently and the workflow is started by hand. Pushing `vX` *alone* would start
   a real release run on the push event instead — do not.
3. **Rehearse.** `gh workflow run release.yml --ref main -f tag=vX -f rehearse=true`. The run
   waits on the `release` environment for its reviewer, then checks the tag against `HEAD`,
   every manifest against the tag, the four Go module tags, tri-core agreement, npm
   provenance's preconditions, dry-run packs of the four npm packages and the four crates,
   and the Python sdist and wheel. **A rehearsal cannot prove a credential**: a dry run never
   authenticates, and neither registry validates a trusted-publisher configuration when it is
   saved. It also cannot verify a dependent crate: the floor was deliberately not uploaded,
   so `sdk`, `cli` and `server` fail to resolve it, and that one failure — in either of the
   two ways cargo spells it — is tolerated in a rehearsal and nowhere else.
4. **Release.** The same dispatch with `rehearse=false`. It waits at the environment gate
   again — the reviewer's approval is the publish decision — then publishes in dependency
   order, waits for each registry to *serve* what it accepted, runs the **outside
   consumers** ([`conformance/consumers/`](conformance/consumers/): the sdk and the floor
   installed from npmjs, crates.io and the Go proxy into empty directories with empty
   caches, no link, path, replace or workspace reachable, then run — a domain signature
   verifies only in its domain, possession goes through the floor, the identity key is
   refused), and creates the GitHub release with `--verify-tag`.
5. **Read the run, not the exit code.** Each publish step skips what its registry already
   has, so a run that failed after uploading is re-run with the same dispatch and finishes
   the rest. "The publish steps SUCCEEDED — check the registry before assuming the release
   failed" is printed by the round-trip steps for exactly this reason.

The workflow file a dispatch runs is **main's**, while the source it checks out is the tag's.
A workflow fix therefore applies to an already-tagged release without re-tagging; a source
fix does not, and needs the next version.

| crates.io | `bitspark-archon-core`, `-sdk`, `-server`, `-cli` (the prefix is a registry name; the library targets are `archon_*`) | trusted publishing via `rust-lang/crates-io-auth-action`; `CARGO_REGISTRY_TOKEN` remains only as the fallback and can be deleted once a release has gone out on OIDC | `vars.CRATES_IO_TRUSTED_PUBLISHING=true` |
| Go proxy + checksum database | `github.com/Bitspark/archon/{core,sdk,cli,server}/go` | none — the tags | the five tags |
| PyPI | `bitspark-archon-core` (import `archon_core`) | trusted publishing via `pypa/gh-action-pypi-publish`; a **pending** publisher may be registered before the project exists — project `bitspark-archon-core`, owner `Bitspark`, repository `archon`, workflow `release.yml`, environment `release` — so no token is ever needed | `vars.PYPI_TRUSTED_PUBLISHING=true`; unarmed, the distributions are built and the run **warns** instead of failing after npm and crates.io have published |
| PyPI | `bitspark-archon-sdk` (import `archon_sdk`), after the floor | the same, and **its own** pending publisher — a trusted publisher is per project, so the core's registration does not cover it: project `bitspark-archon-sdk`, owner `Bitspark`, repository `archon`, workflow `release.yml`, environment `release`. Set it only after the registration exists: armed, its round trip polls for a project that cannot appear, and a red verification withholds the GitHub release |
| Maven Central (`dev.bitspark`) | `dev.bitspark:archon-core` | repository secrets `MAVEN_CENTRAL_USERNAME` / `MAVEN_CENTRAL_PASSWORD` (a Central Portal token pair, not a login) and `MAVEN_GPG_PRIVATE_KEY` / `MAVEN_GPG_PASSPHRASE` (fingerprint `A49669B73C7462D05870C0DECB3E10222F8E5BBB`, public key on `keyserver.ubuntu.com`); the same pair and key that published `dev.bitspark:bitwire` | installed 2026-09-21; first used for 0.7.0, whose credential diagnostic passed before npm published |

Trusted-publisher fields are case-sensitive and unvalidated at save time; a typo is an auth
failure at publish time. A Maven 401 is not evidence that a secret was mis-set: Bitwire's
investigation showed a credential pair reaching Maven unchanged and being refused by Central
itself, and a fresh pair succeeding — diagnose with a read-only request before rotating.

## Recovery

If a run fails after some registry accepted an upload: keep the tag, keep the artifacts,
inspect the registry before doing anything, and re-dispatch with **`verify_only=true`** —
every publish step is skipped, every outside consumer runs against what the registries
serve, and the GitHub release is created. That is the recovery for a good release with a
slow registry, which has now happened twice (0.6.2: npm served 0.6.2 more than five
minutes after accepting it; 0.7.0: Central was still `PUBLISHING` ten minutes after
validating the bundle). Every publish step now skips a version its registry already serves —
but Central's skip can only see a version once Central *serves* it. In the `PUBLISHING` window
between validation and serving, the check says "absent" while Central would still refuse a
second upload, so **do not re-run the failed job while Central is `PUBLISHING`**: use
`verify_only`, or wait until the artifact is served and re-dispatch.
A consumer check that fails after an upload does not mean the upload failed; the registries
serve later than they accept, and the round trips wait for that with a bounded retry. Never
replace a published version with changed source. A registry is "published" in the matrix
only when its public, unauthenticated installation check has passed.

**For Maven Central, verification is a second act — normal, not recovery.** The
other registries serve fast enough to verify in the run that published them. Central does
not: for archon-core 0.7.0 it validated the bundle at 15:15:38Z and served it at 15:59:40Z
— **44 minutes** — against a job whose entire remaining budget was about 37, so no in-run
wait could have covered it.
So the Maven Central consumer runs **only** under `verify_only`, and the publish run asks
the Portal what state the deployment is in instead. Expect two runs for a Java release: one
that publishes, one that verifies. A publish run that ends green has not proved Central
serves anything, and the matrix should not say "published" until the second run is green.

The second run does not have to be `verify_only`. A full re-dispatch works too, and is what
finished 0.7.0: every publish step skips a version its registry already serves, the Maven
step records that it skipped, and the Central consumer runs on that signal — an artifact
already being served has no propagation left to wait for. One dispatch, one approval, and
the release is finished and verified.

## Consumed from the tag: C++, Swift, Haskell

These three are not uploaded anywhere. They are consumed from the immutable public tag —
SwiftPM through the Git URL (`Package.swift` is at the repository root because SwiftPM cannot
be pointed at a subdirectory), C++ as tagged source with an installed CMake package, Haskell
through Cabal's `source-repository-package` with `subdir: core/hs` (Hackage deferred). All
three bind OpenSSL ≥ 3.2 to sign and libsodium ≥ 1.0.21 to enforce the profile — see
[ADR 0008 §8](docs/architecture/decisions/0008-the-ed25519-verification-profile.md).

So the release workflow has nothing to publish for them, and their proof is
[`verify-source`](.github/workflows/verify-source.yml): dispatched with a tag after the
release, it resolves the tag on the public remote, clones it, and builds each core's own
consumer against it as a stranger would. **Their rows in the matrix say "published" only once
that run is green for the tag in question.** A tag cut before a core existed cannot verify it,
and the workflow says so rather than failing obscurely.
